# Ведалина: как формируется RAG

**Русский** · [English](vedalina_rag_pipeline.en.md)

Дата фиксации: 2026-08-27, обновлено 2026-09-08.

На MVP-этапе у VEDAL нет отдельного приватного корпуса документов. Поэтому
корпус знаний Ведалины формируется из публичного сайта и всех материалов,
которые Михаил загружает в S3/портал для VEDAL.

## Куда класть документы

Документ нельзя класть только прямой загрузкой в S3 и считать, что он попал в
поиск. Нужны две части:

1. файл в Object Storage;
2. карточка документа в PostgreSQL.

Правильные точки загрузки:

| Тип материала | Куда кладём | Что должно появиться в БД |
| --- | --- | --- |
| Фото, фоновые изображения, медиа сайта | `vedal-media` | ссылка в карточке страницы, продукта или новости |
| PDF, каталоги, буклеты, лицензии, описания изделий | `vedal-documents` | запись `document`: название, продукт, язык, тип, статус, `storage_key` |
| Текст страниц сайта | CMS/админка | запись страницы/новости/продукта |

На стенде загрузка должна идти через админку или импорт-скрипт. Тогда портал
сам кладёт файл в S3, сохраняет `storage_key` в PostgreSQL и отдаёт материал
Ведалине на индексацию.

## Как работает конвейер

```text
Админка / импорт
  -> S3: файл
  -> PostgreSQL: карточка документа
  -> очередь индексации
  -> извлечение текста из PDF/DOCX/HTML
  -> чанки по 500-1000 токенов с overlap
  -> embeddings
  -> PostgreSQL + pgvector
  -> поиск top-k чанков
  -> YandexGPT получает вопрос + найденные чанки
  -> ответ Ведалины со ссылками на источники
```

## PostgreSQL и pgvector

Сделано. Один PostgreSQL, образ `pgvector/pgvector:pg16` — тот же
PostgreSQL 16, что стоял раньше, плюс расширение. Схему заводит миграция
`V34__knowledge_vectors.sql`; она же первой строкой делает
`create extension if not exists vector`. В Managed PostgreSQL расширение
включается в консоли облака, и там эта строка выполняется вхолостую.

### Смена образа на живом томе: предупреждение о сортировке

Поймано 8 сентября при первом же подъёме стека на новом образе, и на
стенде повторится — там том с данными, а не пустой:

```
WARNING: database "vedal" has a collation version mismatch
DETAIL:  The database was created using collation version 2.41,
         but the operating system provides version 2.36.
```

Что произошло. Образ `postgres:16` и образ `pgvector/pgvector:pg16` собраны
на разных версиях системной библиотеки, а порядок сортировки строк берётся
из неё. Том остался прежним, PostgreSQL — той же версии, но правило
«что раньше в алфавите» под ним поменялось. Индексы по текстовым колонкам
построены по старому правилу, и с этого момента база о них знает, что они
могут врать: искать по индексу, отсортированному иначе, чем сравнивает
сама база, — это пропущенные строки в выдаче, а не ошибка на экране.

Само по себе предупреждение ничего не чинит и не ломает: оно повторяется
на каждый запрос и ждёт, пока человек примет решение.

Лечится двумя командами, в этом порядке:

```bash
docker exec vedal-db psql -U vedal -d vedal -c "REINDEX DATABASE vedal;"
docker exec vedal-db psql -U vedal -d vedal -c "ALTER DATABASE vedal REFRESH COLLATION VERSION;"
```

Сначала перестроить индексы по новому правилу, и только потом сказать базе,
что версия принята. Обратный порядок снимает предупреждение, оставляя
индексы старыми, — то есть прячет ровно то, о чём предупреждали.

На стенде `REINDEX DATABASE` блокирует таблицы на время работы. База там
небольшая, счёт идёт на секунды, но делать это стоит в то же окно, что и
выкатку, а не при живых посетителях.

Проверено локально: после двух команд предупреждение не появляется,
данные на месте.

Две таблицы:

`knowledge_source` — материал портала:

| Колонка | Что в ней |
| --- | --- |
| `kind` | `product`, `news`, `document`, `page` |
| `external_id` | slug материала у его модуля; пара с `kind` уникальна |
| `title`, `url` | что показать под ответом и куда вести читателя |
| `visibility` | `public` или `internal` |
| `language` | язык материала |
| `checksum` | отпечаток текста: совпал — не переиндексируем |
| `indexed_at` | когда индексировали |

`knowledge_chunk` — фрагмент и его вектор:

| Колонка | Что в ней |
| --- | --- |
| `source_id` | материал; удаление уносит чанки каскадом |
| `position` | номер фрагмента внутри материала |
| `text` | сам фрагмент — ровно он попадает в контекст модели |
| `model` | чем посчитан вектор |
| `embedding` | `vector(256)` |

Индексов два: `hnsw (embedding vector_cosine_ops)` для поиска по близости
и обычный по `source_id` для переиндексации. HNSW, а не IVFFlat: второй
строит списки по существующим данным и на пустой таблице бессмыслен —
его пришлось бы создавать отдельной миграцией в день появления корпуса.

Чего в схеме нет намеренно:

- **уровня `confidential`.** §7.4 отдаёт такие документы «только по отдельному
  разрешению», и вход сотрудника разрешением не является. Такой материал
  в индекс не попадает вовсе — не фильтруется на выдаче, а физически
  отсутствует. Фильтр на выдаче однажды забыли бы в новом запросе;
  отсутствующей строки забыть нельзя;
- **второй колонки под другую размерность.** Векторы разных моделей
  несравнимы, и сравнивать их всё равно нечем. Смена модели эмбеддингов —
  это отдельная миграция и полная переиндексация.

`checksum` считается по тексту вместе с заголовком, адресом и **именем
модели**: у PDF меняются метаданные и дата, а текст остаётся тем же, и
отпечаток по байтам файла заставлял бы переиндексировать неизменившееся.
Имя модели в отпечатке нужно затем, чтобы смена модели не оставила старые
векторы в индексе мёртвым грузом.

## Размерность и модель

Провайдер эмбеддингов — `VEDAL_RAG_PROVIDER`: `yandex` (по умолчанию,
наследует `VEDAL_LLM_PROVIDER`) или `gigachat`. Ниже — про Яндекс; про Сбер
и переиндексацию при смене провайдера —
[gigachat_activation.md](gigachat_activation.md#поиск-по-близости-pgvector-и-переиндексация).

Эмбеддинги Яндекса — Yandex Foundation Models, дверь
`foundationModels/v1/textEmbedding`, ключ тот же, что у YandexGPT.

Моделей **две**, и это не дублирование: `text-search-doc` кодирует фрагменты
документов, `text-search-query` — вопросы. Это пара, векторы попадают в одно
пространство именно потому, что модели разные. Перепутать их — не отказ,
а тихо испорченная выдача.

Длина вектора — 256, и это число прошито в типе колонки: pgvector требует
размерность, иначе колонку нельзя проиндексировать. Портал не верит числу
на слово — длина пришедшего вектора сверяется с ожидаемой, и расхождение
роняет индексацию с внятным сообщением. Иначе смена модели была бы заметна
не по отказу, а по тому, что ответы стали хуже.

Сверка идёт и раньше первой индексации — на старте: `KnowledgeStore`
читает размерность колонки из `pg_attribute` и сравнивает с моделью.
У GigaChat вектор длины 1024, и портал с `VEDAL_RAG_PROVIDER=gigachat`
поверх колонки `vector(256)` не поднимется, а скажет, что нужна миграция
колонки и полная переиндексация.

## Как это связано с YandexGPT

YandexGPT не хранит наши документы. Он получает только временный контекст в
момент ответа:

1. посетитель пишет вопрос;
2. backend превращает вопрос в embedding;
3. PostgreSQL/pgvector находит ближайшие чанки;
4. backend собирает prompt: правила Ведалины + найденные выдержки + вопрос;
5. YandexGPT генерирует ответ;
6. backend проверяет guardrails и отдаёт ответ на сайт.

Если похожих чанков нет, Ведалина не придумывает ответ и переводит вопрос к
специалисту.

## Что индексируем сейчас

Сегодня, до корпуса, индексируется то, что портал и так показывает:
опубликованные изделия, новости и карточки документов. Берётся оно через те же
запросные интерфейсы соседей, что и в поиске по словам, — ни одного нового
поля и ни одного нового источника.

Файлы тоже: текст опубликованного PDF или DOCX извлекается и приклеивается
к карточке документа. Скан отдаёт пустой текст — такой документ индексируется
одной карточкой и не стоит ни одного вызова модели.

Индексируем:

- страницы публичного сайта;
- опубликованные продукты;
- новости;
- документы, загруженные для сайта;
- PDF/буклеты/каталоги, которые Михаил добавляет в S3 и регистрирует в портале.

Не индексируем:

- пароли, ключи, договорные секреты и учётные записи;
- черновики, если они не отмечены как материал для сайта;
- персональные данные из заявок;
- логи чатов и служебный аудит.

Если позже ВЕДАЛ передаст документы с ограниченным доступом, вводим второй
контур индексации с правами доступа. На текущем этапе весь переданный корпус
для сайта считается публичным корпусом Ведалины.

## Какие порты нужны

Для RAG не нужно открывать наружу PostgreSQL, Kafka или S3-ключи.

Наружу нужны только:

- сайт/API: `18080` на текущем стенде, затем `443`;
- Keycloak для входа сотрудников: временно `18180`, затем HTTPS через домен;
- SSH: `2222` только по точным IP/VPN.

Всё остальное работает внутри ВМ или через исходящий HTTPS:

- backend читает S3 по сервисному ключу;
- backend вызывает YandexGPT по HTTPS;
- PostgreSQL/pgvector живёт в Docker network;
- Kafka/очередь индексации живёт в Docker network.

## Что сделано и что ждёт корпуса

Состояние на 9 сентября 2026,
[issue #38](https://github.com/michaelwelly/MuseonUrania/issues/38).

Сделано — всё, что не зависит от содержимого документов:

1. PostgreSQL переведён на образ с `pgvector`; тесты поднимают тот же образ.
2. Миграция `V34` заводит `knowledge_source` и `knowledge_chunk`.
3. Нарезка материала на фрагменты с перекрытием (`Chunks`).
4. Порт эмбеддингов `Embeddings` и его реализация `YandexEmbeddings`.
5. Индексация с отпечатком (`KnowledgeIndex`): неизменившийся материал
   не стоит ни одного вызова модели.
6. Поиск по близости с порогом и областями `PUBLIC` / `STAFF`
   (`VectorSearch`).
7. Переход, а не замена (`RagRetrieval`): не нашлось в индексе — отвечает
   прежний поиск по словам.
8. Переиндексация того, что портал показывает сегодня, — изделий, новостей
   и карточек документов.
9. **Извлечение текста из PDF и DOCX** (`FileText`). PDF разбирает PDFBox;
   DOCX портал читает сам — это ZIP с одной частью XML, и библиотека офисных
   форматов ради него в образ не едет. Файл приезжает от того, кто его
   загрузил, поэтому обе дороги обрезаны: внешние сущности XML выключены,
   распакованный размер и длина текста ограничены. OCR нет: скан отдаёт
   пустой текст, и это честный ответ — такой документ индексируется карточкой.
10. **Очередь индексации** (`KnowledgeIndexer`). Событие `vedal.documents.v1`
    поднимает переиндексацию одного документа и пишется теперь не только
    на публикацию, но и на правку карточки и замену файла — в той же
    транзакции, что сама правка. Потребитель смотрит перечень заново:
    документ там есть — индексируем, нет — забываем.
11. **Кнопка «переиндексировать» в админке** и состояние индекса рядом с ней:
    `GET` и `POST /api/admin/v1/knowledge`, карточка на странице документов.
    У строки документа видно, ищет ли по нему Ведалина и сколькими
    фрагментами.

Ждёт корпуса:

1. **Калибровка порога** `vedal.assistant.rag.max-distance`. Значение 0.45
   поставлено умолчанием и заведомо неточно: мерить порог можно только
   на настоящих документах и настоящих вопросах. Как мерить — раздел ниже.
2. **Второй контур индексации** для материалов с ограниченным доступом, если
   ВЕДАЛ такие передаст.

## Как калибровать порог, когда появится корпус

`vedal.assistant.rag.max-distance` — это косинусное расстояние, дальше
которого фрагмент считается не относящимся к вопросу. Число одно, и ошибки
у него две, разной цены:

- **порог слишком велик** — в контекст модели попадают чужие фрагменты,
  и Ведалина отвечает уверенно и не по делу. Это худший отказ из возможных:
  посетитель не видит, что ответ собран из непохожего;
- **порог слишком мал** — ассистент передаёт вопрос человеку там, где ответ
  в корпусе был. Это дорого, но заметно и не врёт.

Отсюда правило калибровки: **при равенстве сомнений порог берём меньший.**

Порядок работы:

1. **Собрать корпус и индекс.** Документы загружаются через админку
   (файл в S3 **и** карточка в БД), затем кнопка «переиндексировать».
2. **Составить список вопросов.** Тридцать-пятьдесят настоящих вопросов —
   не придуманных нами, а взятых из переписки с клиентами, из заявок
   и из журнала разговоров Ведалины. Половина должна иметь ответ в корпусе,
   половина — заведомо не иметь. Вторая половина важнее первой: именно
   на ней виден слишком большой порог.
3. **Снять расстояния.** Для каждого вопроса записать расстояние до
   ближайшего фрагмента и то, отвечает ли этот фрагмент на вопрос
   по мнению человека. Порог на время замера ставится заведомо большим
   (например, 0.9), иначе часть измерений просто не появится.
4. **Посмотреть на два облака чисел.** У вопросов с ответом расстояния
   соберутся ниже, у вопросов без ответа — выше. Порог ставится в разрыв
   между ними, ближе к нижнему облаку.
5. **Проверить на отложенных вопросах.** Десяток вопросов, не участвовавших
   в замере. Если на них порог ведёт себя иначе — облака пересекаются,
   и дело не в пороге: значит, нарезка или модель эмбеддингов не подходят
   этому корпусу.

Чего делать не надо:

- **подбирать порог по ощущению от нескольких вопросов.** Одно число,
  выбранное по трём примерам, — это не порог, а совпадение;
- **поднимать порог, чтобы «находилось чаще».** Ведалина не молчит при
  пустой выдаче: она передаёт вопрос человеку. Поднятый порог меняет
  «не нашлось» на «нашлось не то», и второе дороже;
- **мерить на синтетических текстах.** Расстояния зависят от того, как
  устроен настоящий текст: у датащита с таблицами и у новости они разные.

Результат записывается сюда и в `VEDAL_RAG_MAX_DISTANCE` на стенде.
Переиндексация после смены порога не нужна — он применяется на запросе,
а не при индексации.

## Пустой индекс

Это главное свойство сделанного, и оно проверяется тестами.

Пустой индекс — рабочее состояние, а не заготовка. Поиск по нему возвращает
ноль строк, `RagRetrieval` передаёт слово поиску по словам, и ассистент
отвечает ровно так же, как отвечал до pgvector. Ни отказа, ни выдуманного
ответа.

Пустой индекс к тому же ничего не стоит: прежде чем считать вектор вопроса —
а это вызов модели, то есть счёт, — портал спрашивает базу, есть ли вообще
что искать. Пока корпуса нет, это единственный запрос сверх прежнего.

То же и с молчанием облака: отказ эмбеддингов означает «векторный поиск
ничего не дал», а не «ассистент сломался».

## Как включить

По умолчанию выключено. Индексировать нечего, и каждый вопрос стоил бы
вызова эмбеддингов ради заведомо пустой выдачи.

```env
VEDAL_RAG_ENABLED=true
VEDAL_RAG_DOCUMENT_MODEL_URI=emb://<folder_id>/text-search-doc/latest
VEDAL_RAG_QUERY_MODEL_URI=emb://<folder_id>/text-search-query/latest
VEDAL_RAG_MAX_DISTANCE=0.45
```

Ключ отдельный не нужен — берётся `VEDAL_YANDEXGPT_API_KEY`: эмбеддинги живут
в том же Foundation Models и оплачиваются тем же сервисным аккаунтом.
С `VEDAL_RAG_PROVIDER=gigachat` пара адресов не нужна, вместо неё —
`GIGACHAT_EMBEDDINGS_MODEL` и ключ `GIGACHAT_AUTH_KEY`.

Половинчатая настройка роняет старт с внятным сообщением: включённый режим
без ключа — это портал, который молча работает наполовину, и заметить такое
можно было бы только по тому, что ответы стали хуже.
