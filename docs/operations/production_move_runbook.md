[production_move.md](production_move.md) отвечает на вопрос «что делать»

## 1. Переменные `compose.prod.yaml`

Список получен не на глаз, а прогоном самой валидации, которую отказывается
проходить конфигурация без каждой из них:

```bash
docker compose -f backend/compose.yaml -f backend/compose.prod.yaml \
  --profile app config
```

Она добавляет переменные в сообщение об ошибке по одной, пока набор не
станет полным (`docker compose config` останавливается на первой
недостающей). Полный список — тот, с которым команда выше отработала без
ошибок:

```bash
grep -oE 'VEDAL_[A-Z0-9_]+:\?' backend/compose.prod.yaml | sort -u
```

**Не пытаться поднимать этот конфиг целиком на текущей ВМ.** `--profile app
up` без `config` поднимает `proxy` и займёт `80`/`443` — те же порты, что
держит `c3ag.ru`. Проверять можно только `config` (генерацию итогового
YAML), не `up`.

### 1.1. Обязательные — без них `docker compose ... config` падает

| Переменная | Где используется | Значение и откуда его брать |
| --- | --- | --- |
| `VEDAL_DOMAIN` | `proxy` (Caddy, домен сайта) | `vedal-med.ru`. Домен из #36. |
| `VEDAL_KEYCLOAK_DOMAIN` | `proxy` (свой vhost Keycloak) | `id.vedal-med.ru` — поддомен, не путь на основном домене (своя cookie). |
| `VEDAL_MEDIA_DOMAIN` | `proxy` (CSP `img-src`) | `media.vedal-med.ru` — хост из `VEDAL_MEDIA_URL`, CNAME на бакет. |
| `VEDAL_DB_NAME` | `db`, `connect`, `portal` | `vedal`. Совпадает с текущим — иначе это уже не перенос, а новая база. |
| `VEDAL_DB_USER` | `db`, `connect`, `portal` (миграции), `keycloak` | `vedal` — владелец схемы, тот же, под кем сняли бэкап на старой машине. |
| `VEDAL_DB_PASSWORD` | `db`, `connect`, `portal`, `keycloak` | Новый пароль владельца схемы на новой машине — не обязан совпадать со старым, это внутренний docker-сети пароль. Сгенерировать: `openssl rand -base64 24`. |
| `VEDAL_RUNTIME_PASSWORD` | `db` (init-скрипт роли `vedal_app`), `portal` | Новый пароль роли рантайма. Тоже генерируется заново — роль создаётся init-скриптом на пустом томе новой машины, старый пароль ей не наследуется. |
| `VEDAL_KEYCLOAK_URL` | `keycloak` (`KC_HOSTNAME`), `portal` (`VEDAL_OIDC_ISSUER`), `api-gateway`, `site` | `https://id.vedal-med.ru`. Обязан совпадать с адресом, по которому реально ходит браузер сотрудника — иначе портал отвергает токен по `issuer`. |
| `VEDAL_KEYCLOAK_ADMIN` | `keycloak` (`KC_BOOTSTRAP_ADMIN_USERNAME`) | Логин администратора самого Keycloak (не портала). Придумать новый, не переносить со стенда. |
| `VEDAL_KEYCLOAK_ADMIN_PASSWORD` | `keycloak` | Новый пароль: `openssl rand -base64 24`. |
| `VEDAL_OIDC_SVC_CLIENT_SECRET` | `keycloak` (подставляется в realm при импорте), `portal` | Новый секрет служебного клиента `vedal-portal-svc`: `openssl rand -base64 32`. Значение уходит в **оба** места одной переменной — сгенерировать один раз. |
| `VEDAL_S3_ACCESS_KEY` | `portal`, `media-seed` (профиль `seed`, не в `--profile app`) | Ключ сервисного аккаунта Yandex Object Storage, право `storage.editor` на `vedal-media` и `vedal-documents`. Тот же ключ, что и сейчас — хранилище не переезжает. |
| `VEDAL_S3_SECRET_KEY` | `portal` | Секрет к ключу выше. |
| `VEDAL_ALLOWED_ORIGINS` | `portal` (CORS) | `https://vedal-med.ru` — прямое обращение к порталу и локальная разработка сюда не входят. |
| `VEDAL_ADMIN_ORIGINS` | `portal` (CORS админки) | `https://vedal-med.ru`. |
| `VEDAL_PUBLIC_URL` | `portal` (`VEDAL_PORTAL_URL`), `api-gateway`, `site` (`NEXT_PUBLIC_API_URL`) | `https://vedal-med.ru` — адрес, который видит браузер посетителя. |
| `VEDAL_MEDIA_URL` | `site` (`NEXT_PUBLIC_MEDIA_URL`) | `https://media.vedal-med.ru`. Хост этого адреса обязан совпадать с `VEDAL_MEDIA_DOMAIN` — разойдутся, и `img-src` в CSP не пропустит фотографии, а страница откроется целой (см. комментарий в `proxy/Caddyfile`). |

### 1.2. Не обязательные, но без них переезд получится с сюрпризом

Compose поднимется и без них — они падают на встроенные умолчания, которые
для прода не годятся.

| Переменная | Умолчание | Почему всё равно задать на проде |
| --- | --- | --- |
| `VEDAL_ADMIN_ALLOW` | `private_ranges` | Правильное умолчание для двери `/admin` — но раньше эта переменная в контейнер `proxy` вообще не попадала (см. §4). Теперь попадает; если решение — «VPN/бастион», можно не трогать. |
| `VEDAL_ACME_EMAIL` | `admin@localhost` | Тот же пробел из §4. Задать настоящую почту команды — на неё Let's Encrypt пришлёт предупреждение, если продление сертификата сломается. |
| `VEDAL_SITE_URL` (→ `NEXT_PUBLIC_SITE_URL`) | пусто | **Критично для запуска.** Пока пусто, `robots.txt` закрывает сайт от индексации целиком — это защита стенда с черновиками, не то, что нужно боевому сайту. Задать `https://vedal-med.ru` в день выхода на домен. |
| `VEDAL_S3_BUCKET_MEDIA` / `VEDAL_S3_BUCKET_DOCUMENTS` | `vedal-media` / `vedal-documents` | Совпадают с текущими — переносить нечего, но подтвердить явно, а не полагаться на умолчание. |
| `VEDAL_KEYCLOAK_DB_NAME` | `keycloak` | Имя базы Keycloak в том же кластере PostgreSQL. См. §4 — эта база не заводится сама. |
| `VEDAL_BACKUP_KEEP_DAYS` | `7` | Только для встроенного в `compose.prod.yaml` сервиса `backup` — см. §3.3, почему на него лучше не полагаться. |
| `VEDAL_WATCH_MAIL_TO`, `SPRING_MAIL_HOST`, `SPRING_MAIL_USERNAME`, `SPRING_MAIL_PASSWORD` | пусто | Без них сторож пишет тревоги только в свой журнал, который на сервере никто не читает, пока не случится беда — см. [monitoring.md](monitoring.md). Задать до переезда, не после первого инцидента. |
| `VEDAL_NOTIFICATIONS_MANAGER` | пусто | Адрес менеджера для уведомлений о заявках. |
| `VEDAL_GATEWAY_TRUSTED_PROXY` | диапазоны docker-сети | Умолчание безопасно именно потому, что снаружи в docker-сеть не попасть — трогать не нужно, если топология сети не меняется. |
| `VEDAL_METRIKA_ID` (→ `NEXT_PUBLIC_YANDEX_METRIKA_ID`) и `VEDAL_ANALYTICS_ORIGINS` | пусто | Яндекс Метрика, issue #53. Пусто — счётчика нет, и это законное состояние: сайт от аналитики не зависит. Заполняются **только вместе** и **только после ответа заказчика** на вопрос 12.11 в [PROJECT.md](../PROJECT.md): `VEDAL_METRIKA_ID=<номер>`, `VEDAL_ANALYTICS_ORIGINS=https://mc.yandex.ru https://mc.yandex.com`. Номер без источников даёт счётчик, который загрузился и молча не считает — политика безопасности не пустит его запросы, а страница останется целой. |

## 2. Что завести до дня X

Ничего из этого раздела не делается в ночь переезда — если что-то из
списка не готово к дню X, дата двигается, а не компенсируется скоростью.

1. **Новая ВМ.** Yandex Cloud, отдельная от `smart_soultion_mvp` — без
   соседства с `c3ag.ru`. Docker + Docker Compose плагин установлены,
   репозиторий склонирован в `/opt/vedal-portal` (по образцу
   «vedal_vm_deploy_plan_2026-08-18.md» (`outputs/server/vedal_vm_deploy_plan_2026-08-18.md` — вынесен из публичного репозитория, см. [чистку 8 сентября](../security/public_repo_cleanup_2026-09-08.md)), раздел 3).
2. **Security group.** `80` и `443` открыты всему интернету (иначе Caddy не
   получит сертификат и посетитель не откроет сайт). SSH — только по
   точным IP команды, по нестандартному порту, как сейчас на старой ВМ.
   Больше **ничего** наружу: ни `5434`, ни `9092`, ни `8083`, ни прямого
   порта Keycloak — в этом весь смысл переезда на `compose.prod.yaml`
   (см. [production_move.md](production_move.md), §2.3).
3. **DNS.** Доступ к зоне `vedal-med.ru` подтверждён. TTL записей понижен
   заранее, минимум за сутки — иначе откат работает медленнее, чем идёт
   само переключение (правило то же, что в
   [domain_cutover_vedal_med_ru.md](domain_cutover_vedal_med_ru.md)).
   Текущие записи сняты и сохранены дословно — план отката.
4. **Ключ объектного хранилища с правом записи в `vedal-backups`.**
   Сейчас, по [backups.md](backups.md), ключ на машине умеет только читать,
   и копии бэкапа не уезжают за пределы ВМ. На новой машине задать
   `VEDAL_BACKUP_S3_BUCKET` и ключ с ролью `storage.editor` — иначе перенос
   площадки повторяет тот же риск («упала ВМ — упала единственная копия»),
   ради снятия которого и затевался.
5. **Список сотрудников Keycloak.** Выгрузить вручную из консоли Keycloak
   старого стенда (Users → экспорт списка логинов и ролей) **до** отключения
   старой машины. Это не формальность — см. предупреждение в §4.2: учётные
   записи сотрудников не переносятся автоматически.
6. **Секреты подготовлены заранее**, не придумываются в терминале в 3 часа
   ночи: `backend/.env` на новой машине собран по таблице §1, значения
   сгенерированы (`openssl rand -base64 24/32`), сохранены в менеджере
   паролей команды.
7. **systemd-юниты установлены, но не включены**: `vedal-backup.timer`
   ([backups.md](backups.md)), `vedal-health.timer`
   ([monitoring.md](monitoring.md)), `vedal-autodeploy.timer`
   ([autodeploy.md](autodeploy.md)). Установка — `sudo systemctl enable`
   без `--now`: включать после того, как стек поднят и проверен, не раньше.
8. **`backend/keycloak/prod/vedal-realm.json` просмотрен глазами** — какие
   клиенты и роли в нём заведены, что в нём заведён только один служебный
   технический пользователь (`service-account-vedal-portal-svc`) и **ни
   одной учётной записи сотрудника** осознанно (см. §4.2).

## 3. День переезда

### 3.1. Заморозка старой машины

1. Предупредить, что портал уходит в обслуживание — форма заявки и админка
   недоступны на время переноса.
2. На старой ВМ остановить только пишущие сервисы, чтобы дамп снимался
   с неподвижной базы:
   ```bash
   ssh -p 2222 ubuntu@51.250.31.97
   cd /opt/vedal-portal
   docker compose -f backend/compose.yaml -f backend/compose.stand-prod.yaml \
     --profile app stop portal api-gateway site
   ```
   База (`vedal-db`) и Keycloak остаются работать — дамп снимается `pg_dump`
   без блокировки на чтение, а Keycloak не пишет ничего, что важно захватить
   (см. §4.2 — его данные всё равно не переезжают этим дампом).

### 3.2. Финальный дамп

```bash
# на старой ВМ, вручную, не дожидаясь трёх часов ночи по таймеру
sudo systemctl start vedal-backup.service
journalctl -u vedal-backup -n 30 --no-pager
ls -la /var/backups/vedal/daily/   # взять самый свежий *.dump
```

Прогон уже проверяет себя восстановлением и падает, если дамп меньше
10 КБ или в восстановленной копии меньше 20 таблиц — если команда выше
завершилась нулём, дамп годный для переноса (детали — [backups.md](backups.md)).

Скопировать дамп на новую машину:

```bash
scp -P 2222 ubuntu@51.250.31.97:/var/backups/vedal/daily/vedal-<штамп>.dump \
  ./vedal-move.dump
scp -P <порт-новой-ВМ> ./vedal-move.dump ubuntu@<новая-ВМ>:/tmp/vedal-move.dump
```

### 3.3. Поднять окружение на новой машине БЕЗ приложений

Команды в этом и следующих разделах опираются на `$VEDAL_DB_USER` и
`$VEDAL_DB_NAME` из `backend/.env` — прежде чем их копировать, подгрузить
файл в переменные окружения сессии:

```bash
cd /opt/vedal-portal
set -a; source backend/.env; set +a
```

```bash
docker compose -f backend/compose.yaml -f backend/compose.prod.yaml \
  up -d db kafka keycloak connect
docker compose -f backend/compose.yaml -f backend/compose.prod.yaml logs -f db
```

Дождаться `healthy` у `db`. Это создаёт **пустой** том — на нём при первом
старте `postgres` выполнит init-скрипты
(`backend/db/init/10-runtime-role.sh` и `20-keycloak-db.sh`): заведёт роль
`vedal_app` и базу `keycloak`. Проверить, что оба действительно появились,
**до** восстановления дампа:

```bash
docker exec vedal-db psql -U "$VEDAL_DB_USER" -d postgres \
  -c "select rolname from pg_roles where rolname = 'vedal_app'"
docker exec vedal-db psql -U "$VEDAL_DB_USER" -d postgres \
  -c "select datname from pg_database where datname = 'keycloak'"
```

Обе строки должны вернуться непустыми. Если пусто — том не был пустым при
старте (переиспользованный volume), и роль/базу придётся завести руками
командами из комментариев в самих init-файлах, **прежде чем** идти дальше.

**Про сервис `backup` из `compose.prod.yaml` — не запускать.** Он поднят в
профиле `app` и, если стартовать весь профиль сразу, включится сам —
но это отдельный, никогда не проверенный на этом стенде механизм: свой
цикл `pg_dump` раз в сутки в отдельный docker-том, без проверки
восстановлением и без выгрузки за пределы машины (сравните с
[backups.md](backups.md)). Держать два независимых бэкапа одной базы —
не подстраховка, а гарантированная путаница «какому дампу верить» в день,
когда он понадобится. Использовать `scripts/backup.sh` + `vedal-backup.timer`
как единственный источник правды; сервис `backup` в compose можно оставить
невключённым (не поднимать его контейнер) до отдельного решения о том,
дублировать его или удалить.

### 3.4. Восстановить дамп

```bash
docker exec -i vedal-db pg_restore -U "$VEDAL_DB_USER" -d "$VEDAL_DB_NAME" \
  --no-owner --role="$VEDAL_DB_USER" < /tmp/vedal-move.dump
```

`--no-owner` обязателен: без него `pg_restore` пытается назначить владельцем
объектов роль, под которой снимался дамп на старой машине, — а это тот же
`vedal` (переменная не менялась, см. §1.1), так что на практике совпадёт,
но полагаться на совпадение имён не стоит: `--no-owner` делает восстановление
владельцем **той роли, что подключилась**, то есть `VEDAL_DB_USER` новой
машины, каким бы он ни был.

Проверить количество строк в паре ключевых таблиц — не «restore прошёл без
ошибок», а «данные те же»:

```bash
docker exec vedal-db psql -U "$VEDAL_DB_USER" -d "$VEDAL_DB_NAME" \
  -c "select count(*) from lead" \
  -c "select count(*) from product" \
  -c "select count(*) from audit_entry"
```

Сравнить с числами на старой машине (тот же запрос до остановки в §3.1 —
снять их заранее, до заморозки).

### 3.5. Поднять приложения

```bash
docker compose -f backend/compose.yaml -f backend/compose.prod.yaml \
  --profile app up -d --build portal api-gateway site proxy watchdog
```

`backup` из команды выше сознательно не перечислен — см. §3.3.

Дождаться, что `portal`, `api-gateway`, `site` и `proxy` стали `healthy`
(`docker compose ps`), прежде чем переключать DNS.

### 3.6. Создать сотрудников в Keycloak заново

Realm `prod` импортируется без единой учётной записи сотрудника — так
и задумано: в `vedal-realm.json` заведён только служебный технический
пользователь `service-account-vedal-portal-svc` (комментарий в
`compose.prod.yaml` рядом с томами `keycloak`: «в нём нет ни одного
пользователя: сотрудников заводит тот, кто держит Keycloak, а не файл
в репозитории»). Список из §2.5 заводится вручную через
консоль нового Keycloak (`https://id.vedal-med.ru/admin/`, логин —
`VEDAL_KEYCLOAK_ADMIN` из §1.1): Users → Add user, назначить роли
`portal-admin`/`portal-editor`, включить обязательный второй фактор при
первом входе (realm `prod` требует его политикой). Пароли — временные,
сотрудник меняет при первом входе.

### 3.7. Переключить DNS

```
vedal-med.ru.      A     <IP новой ВМ>
www.vedal-med.ru.  CNAME vedal-med.ru.
id.vedal-med.ru.   A     <IP новой ВМ>
```

`media.vedal-med.ru` не трогается — он уже указывает на объектное хранилище
и остаётся так же, площадка сайта на это не влияет ([Caddyfile](../../backend/proxy/Caddyfile),
раздел «медиа»).

Проверить перед тем, как ждать полного распространения:

```bash
dig +short vedal-med.ru
curl -sv --resolve vedal-med.ru:443:<IP новой ВМ> https://vedal-med.ru/ -o /dev/null
```

Второй `curl` подделывает DNS локально и проверяет сайт по имени раньше,
чем разойдётся настоящий DNS — так же, как HTTPS проверялся при
подключении домена (см. [domain_cutover_vedal_med_ru.md](domain_cutover_vedal_med_ru.md),
шаг 1.4).

## 4. Подводные камни переноса базы

### 4.1. Формат и версия

Дамп снят `pg_dump -Fc` (`scripts/backup.sh`) внутри контейнера с образом
`postgres:16` — тем же, что прописан в `backend/compose.yaml` для новой
машины. Пока образ не меняют вручную на другой тег, `pg_restore` той же
мажорной версии восстанавливает дамп той же версии без сюрпризов; кросс-
версийного переноса (например, на будущий Managed PostgreSQL другой минорной
версии) в рамках этого переезда нет — тот шаг стоит отдельно и после
переезда площадки, по рекомендации [production_move.md](production_move.md).
Расширений PostgreSQL (`create extension`) в проекте не используется ни
одного — переносить, кроме роли и данных, нечего.

### 4.2. Keycloak — данные не в дампе базы `vedal`

Это самый нетривиальный камень, и его легко не заметить, потому что всё
остальное «просто работает».

Сейчас (и на локальном стеке, и на текущем стенде — `compose.stand-prod.yaml`
накладывается на `compose.yaml`, не на `compose.prod.yaml`) Keycloak
запускается командой `start-dev` **без** `KC_DB` — то есть на встроенной
файловой базе H2 внутри тома `vedal-keycloak`. Все учётные записи
сотрудников, их пароли, второй фактор и настройки realm живут в этом файле,
а не в PostgreSQL.

`compose.prod.yaml` переводит Keycloak в `KC_DB: postgres`, отдельную базу
`keycloak` в том же кластере — **другое хранилище**, не миграция старого.
Ни `pg_dump`/`pg_restore` базы `vedal`, ни копирование тома `vedal-keycloak`
эти данные не перенесут: новый Keycloak стартует с чистой базой `keycloak`
и накатывает в неё только то, что лежит в `backend/keycloak/prod/vedal-realm.json`
— клиентов, роли и один служебный технический пользователь для
`vedal-portal-svc`, но **ни одной учётной записи сотрудника** (см. §3.6).

Из этого два следствия:

- список сотрудников собирается заранее (§2.5) и заводится заново после
  переезда (§3.6) — это ручная работа, а не часть восстановления дампа;
- если до переезда через Keycloak уже включён обязательный второй фактор
  кому-то из сотрудников, это тоже придётся настраивать заново — сохранённых
  кодов восстановления в realm-файле нет и быть не может.

### 4.3. Роль `vedal_app` — порядок имеет значение

Дамп содержит не только данные, но и `GRANT`, которые миграции V15/V16
выдали роли `vedal_app` на момент снятия дампа (`pg_dump` без `--no-acl`
сохраняет права). Если восстанавливать дамп **до** того, как роль
`vedal_app` создана на новой машине, `pg_restore` наткнётся на `GRANT ...
TO vedal_app` для несуществующей роли — по умолчанию `pg_restore`
не останавливается на таких ошибках (нет `--exit-on-error`), просто
пропускает эти строки и идёт дальше, и это самое опасное: восстановление
«прошло», а роль рантайма осталась без части прав, о чём молчаливо
рапортует только код возврата, на который никто не смотрит.

Отсюда жёсткий порядок §3.3 → §3.4: сначала `db` до `healthy` (роль
и база Keycloak уже созданы init-скриптами), только потом `pg_restore`.
Проверка из §3.3 («обе строки должны вернуться непустыми») — это ровно
защита от восстановления в неправильном порядке.

Отдельно: если конечная цель — Managed PostgreSQL (следующий шаг после
этого переезда, см. [production_move.md](production_move.md), §2.2), там
у владельца схемы нет `CREATEROLE`, и `10-runtime-role.sh` не выполнится
вовсе — роль на управляемом кластере заводится консолью или `yc` CLI
**до** наката миграций, это уже описано как условие в комментарии самой
миграции V16.

## 5. Проверка после переключения

Пункты — из протокола прогона [issue #57](https://github.com/michaelwelly/MuseonUrania/issues/57#issuecomment-5573863111):
тот же список, что уже использовался для приёмки стенда, здесь применяется
к боевому домену. Проверять **снаружи**, не изнутри новой ВМ — в отличие от
прогона на стенде, здесь как раз важно, что видит настоящий посетитель
через настоящий DNS и настоящий сертификат.

| Проверка | Как |
| --- | --- |
| Сайт открывается по HTTPS | `curl -svo /dev/null https://vedal-med.ru/` — код `200`, сертификат валиден |
| `c3ag.ru` не пострадал | Отдельный запрос к старой ВМ — она вообще не участвует в новой схеме, но проверить, что её никто не трогал |
| Заявка с сайта | Отправить тестовую заявку, убедиться, что она в админке (`З-2026-xxxx`) |
| Вход в админку | `https://vedal-med.ru/admin/` → форма Keycloak на `https://id.vedal-med.ru` → кабинет → выход |
| Ведалина отвечает по изделию | Вопрос про конкретную модель, ответ со ссылками на источники |
| Публикация новости | Админка: создать черновик → опубликовать → появился в `/api/public/v1/news` → снять → удалить |
| Документы | Скачивание опубликованного — `200`; закрытого — `404` и запись в журнале (`document.access.denied`) |
| Фотографии | `200` на карточках, листинг бакета закрыт |
| `robots.txt` | **Не** `Disallow: /` — в отличие от стенда, боевой сайт обязан быть открыт для индексации (см. `VEDAL_SITE_URL` в §1.2) |
| Журнал: адрес посетителя | В `audit_entry` — настоящий IP клиента, а не адрес `proxy` (тот же баг, что чинили для шлюза — [#58](https://github.com/michaelwelly/MuseonUrania/issues/58)) |
| Дверь `/admin` | Обращение не из приватного диапазона получает `403` с текстом «Дверь правки доступна только из доверенной сети» |
| Сторож пишет тревоги | Временно занизить `VEDAL_WATCH_FAILS`/остановить `portal` на 5 минут, проверить письмо на `VEDAL_WATCH_MAIL_TO` |
| Бэкап новой машины | `sudo systemctl start vedal-backup.service` вручную, убедиться, что дамп снялся и прошёл проверку восстановлением |

## 6. Откат

Старая ВМ **не выключается** до подтверждения (см. §5) — минимум сутки
после переключения, дольше, если DNS ещё не разошёлся у всех.

1. Вернуть DNS-записи, сохранённые в §2.3, дословно.
2. Дождаться истечения старого TTL (для этого он был понижен заранее).
3. На старой ВМ поднять то, что было остановлено в §3.1:
   ```bash
   docker compose -f backend/compose.yaml -f backend/compose.stand-prod.yaml \
     --profile app start portal api-gateway site
   ```
4. Заявки и правки, сделанные за время на новой машине, откатом **теряются**
   — база на старой ВМ не знает о них. Если окно между переключением и
   решением об откате было больше нескольких минут, снять с новой машины
   дамп заявок/новостей за это время и перенести вручную, а не откатывать
   вслепую.
5. Новая ВМ не удаляется — доработать и повторить переключение, а не начинать
   перенос данных заново.
