# API Gateway

**Русский** · [English](README.en.md)

Единая точка входа контура. Из [брифа собственника](../../docs/architecture/vedal_portal_owner_brief.md)
это DMZ / Integration Gateway: снаружи виден один адрес, за ним портал и сайт.

Отдельное приложение, а не модуль портала. `backend/gateway/` — это другое:
там документация модуля приёма заявок, кода в ней нет.

## Зачем он, если портал и так отвечает

Маршрутизация — наименее интересное из того, что он даёт.

**Сайт и API оказываются на одном источнике.** CORS выпадает из периметра
целиком: браузер не делает кросс-доменный запрос, когда домен один. До шлюза
список разрешённых источников был частью конфигурации портала, и ошибка в нём
означала либо сломанные формы, либо открытую дверь.

**Лимит тела и проверка токена стоят в одном месте**, а не в каждом приложении
за шлюзом.

**Настоящий адрес клиента доезжает до портала** одним и тем же способом
независимо от того, что стоит перед шлюзом. Без этого лимит частоты считает всех
посетителей одним клиентом, а аудит пишет адрес прокси вместо адреса
пользователя.

## Чего он не даёт

**Доверия.** Портал проверяет токен сам и отказывает запросу, пришедшему мимо
шлюза. Роли, права и запись в журнал остаются его работой. Раздвоить это решение
значит однажды поймать расхождение, при котором шлюз пускает, а портал
отказывает, — и искать причину в двух конфигурациях сразу.

Проверка токена на шлюзе включается `VEDAL_GATEWAY_VERIFY_TOKENS=true` и делает
ровно одно: отказ приходит на границе, и запрос без токена не доходит до
приложения. Даже в этом режиме шлюз проверяет только подпись и срок — не роли.

## Маршруты

Порядок важен: список разбирается сверху вниз, поэтому частное идёт первым.

| Маршрут | Куда | Особенность |
| --- | --- | --- |
| `/api/admin/**` | портал | лимит тела 21 МБ — 20 на файл плюс запас на поля формы |
| `/api/**` | портал | публичные двери |
| `/v3/api-docs/**`, `/swagger-ui/**` | портал | springdoc обслуживает их вне префикса `/api` |
| `/**` | сайт | включая `/admin/**` — админку на Next.js |

Маршрута на серверные страницы админки здесь нет, потому что их больше нет
вовсе: у портала не осталось ни одной страницы для браузера, и вместе с ними
ушли форма входа, cookie-сессия и CSRF-токен. Вход идёт в Keycloak напрямую,
`/admin/**` обслуживает сайт.

## Версии

Spring Boot 4.0.8, а не 4.1.0, как у портала. Spring Cloud Gateway 5.0.x собран
под 4.0.x, и это единственная поддерживаемая пара.

Расхождение версий здесь безвредно ровно потому, что это отдельный процесс:
с порталом шлюз разговаривает по HTTP, а не по classpath. По той же причине
не заводится общий Maven-реактор — он навязал бы обоим одну версию Boot.

## Настройки

| Переменная | Значение по умолчанию | Что задаёт |
| --- | --- | --- |
| `VEDAL_GATEWAY_PORT` | `8080` | порт шлюза |
| `VEDAL_PORTAL_URL` | `http://localhost:8081` | адрес портала |
| `VEDAL_SITE_URL` | `http://localhost:3000` | адрес сайта |
| `VEDAL_GATEWAY_VERIFY_TOKENS` | `false` | проверять ли токен на периметре |
| `VEDAL_OIDC_ISSUER` | пусто | адрес realm'а; обязателен при `verify-tokens=true` |

Лимит тела `21MB` в `application.yaml` согласован с `vedal.storage.max-file-size`
портала. Меньший лимит здесь уронит загрузку с 413 до приложения, и редактор
увидит страницу шлюза вместо разбора причины.

## Запуск

В составе стека:

```bash
docker compose -f backend/compose.yaml --profile app up -d --build
```

Отдельно:

```bash
cd backend/api-gateway && ./mvnw spring-boot:run
```

Живость — `GET /actuator/health`. Остальные endpoint'ы закрыты: перечень
маршрутов шлюза это карта системы, по той же причине портал отдаёт наружу
только health.
